# Architecture 15: code-first init

Draft 0.2, 2026-11-26; settled with the owner, question by question (§10). Uses `.physa/glossary.md` terms only. Serves the owner's idea `code-first-init`. It replaces 02 §2.3 (propose), §2.4's sources, §2.7 (the estimate) and the coverage placement built on them; gather (§2.2), check (§2.5) and review as a PR (§2.6) stay.

## 1. Why

Init proposed capabilities from PRs: one session read every gathered PR and change, in shares on a large repo, and named the capabilities they showed. On Rails it found 50. The owner: "I would also expect there to be well over 2-300 capabilities. its a huge framework. 50 capabilities is extremely low." And: "i don't know that deriving capabilities from prs makes sense. you can map rules and decisions and questions to capabilities with prs, but prs don't necessarily define capabilities. I think the codebase is the best place to find that." Then: "The code defines WHAT it does, and the PRs give the WHY", and "a codebase that is well documented and tested gives you a lot of why."

The owner also asked for less code in init ("the init code seems to be getting complex and bloated") and for no estimate on a legacy codebase: "I'm more in favor of a cap than an estimate."

## 3. The phases

```
gather ─▶ areas ─▶ walk each area ─▶ place ─▶ recover each capability ─▶ consolidate ─▶ check ─▶ review as a PR
 (02 §2.2)  1 session   1 session per area   no session  1 session per capability   merge, areas, lift  (02 §2.5)  (02 §2.6, 12)
```

1. **Gather**, as today (02 §2.2), with a larger PR window (§7).
2. **Areas.** One session reads the list of every source file and divides the repo into areas, each a group of promises with the files that serve them, by promise and across layers. Every source file falls in exactly one area. When the listing is more than one session holds, the session gets it in parts and groups by promise across all of them, never one area set per framework (Q8; Discourse is the first repo run this way, before this is built). An area is init's own scaffolding: it never appears in the map and needs no glossary term (owner: "area is a temporary grouping that drops off after we're done initializing").
   Built as the change areas: `physa init --areas` lists the repo's tracked files and leaves out those marked `linguist-vendored` or `linguist-generated` in `.gitattributes`, binary files (a NUL in the first 8000 bytes) and well-known lock files. One session then names the repo's test, doc and other files as path patterns, and code applies them. `dir/` takes every file under the folder. A pattern with no `/` matches a base name in any folder. Otherwise `*`, `?` and `[...]` match within one path segment, and `**` matches across segments. A file goes to the kind of its most specific pattern, a tie going to test, then doc, then other; a file no pattern names is source. A pattern that matches no file is reported as unused. A pattern that matches every file is dropped, since it would leave no source, and when no source is left the phase stops. The source files then go to one session, or, when the listing is larger than the part size, to parts of up to 70,000 characters (less where the agent's window is smaller). Each part's prompt says it is one of several parts, and gives the overview of every source folder, the areas so far and the part's files; a merge session follows the parts. Every source file must land in exactly one area: a file is claimed by its most specific claim, a tie claims it twice, and a file left out or claimed twice goes back to the same session, for up to two fix rounds, before the phase fails. The record in `.git/physa` holds the split and the areas for the later walk to read; a new gather clears them, and nothing is written to the map. `--areas` is a phase alone, not yet in the full run.
3. **Walk.** One session per area, with read-only tools over the area's code, tests and docs, names its capabilities, each a promise with a footprint: the source files it owns, and the tests and docs that bear on it. Every source file of the area is owned by one capability or named shared with a reason; none is left unclaimed. A session may split its area once into smaller ones, each walked on its own.
   Built as the change walk: `physa init --walk` runs one read-only session per stored area, with Read, Glob and Grep over the repo and no other tool, three at once. Its message gives the area's source files with their line counts, and an overview of the repo's test and doc folders. A session names its capabilities as promises with footprints, each owning source files and naming the tests and docs that bear on it, folders written with a trailing `/`, and names every other source file shared with a reason. A top-level area may instead split once into two or more parts, each walked in its own session and never split again; a part's names come from the split. Code checks every footprint: a source file unclaimed, claimed twice or outside the area; a test that is not a test file, or a doc that is not a doc file; a capability owning no source file; a name repeated, malformed or empty; a part answering with a split. Problems go back to the same session, for up to two fix rounds; an area still not whole fails the phase, and nothing is stored. A name another area took gets a number (`-2`, `-3`), in stored area order, and the result reports each rename. A footprint may also name other files (configuration, fixtures, assets and the like), checked against the split as tests and docs are. The record in `.git/physa` holds the footprints and shared files, each footprint's test, doc and other entries as the session wrote them, cleared by a new gather or new areas. `--walk` is a phase alone, not yet in the full run.
4. **Place.** No session. Each gathered PR and change goes to the capabilities that own most of its files: a source file counts whole, a test or doc shared by k capabilities counts 1/k, and the largest are taken until half the weight is covered, at most three. Placement is a fact of the footprint, not a judgment.
   Built as the change place: `physa init --place` runs with no session, on the stored gather, areas and walk. A source file weighs 1 for the capability that owns it, alone. A test, doc or other file a footprint names weighs 1/k for each of the k capabilities that name it, other files counting as tests and docs do; a source file is never shared this way. A footprint entry naming more than 40 files stays in the footprint but is not used to place, and is reported with its capability and kind, since a whole test folder says nothing about where a PR belongs, where a capability's own few tests do. A gathered PR weighs the files of its changes, and a change no gathered PR holds weighs its own; a change a gathered PR holds follows its PR. For each, the weights are totalled per capability, the largest are taken first until half the total is covered, at most three, with ties broken by name. An item with no files known from the gather is placed nowhere for that reason, and one whose files no capability weighs is placed nowhere because none of its files belongs to a capability; both are counted. The placements go in init's record in `.git/physa`, cleared by a new gather, new areas or a new walk, and nothing is written to the map. `--place` is a phase alone; the full run keeps the coverage placement until remove-propose.
5. **Recover.** One session per capability, with read-only tools, is given its placed PRs and changes whole and reads its tests, docs and code comments, and writes its rules, decisions, questions and terms (§6).
   Built as the change recover: `physa init --recover` has two sources and says which it used. When the walk and the placements are both stored, which a new gather, new areas or a new walk keeps current, each walk capability is recovered from them; otherwise recovery reads the stored proposal as before, so the full run (gather, propose, recover) is unchanged until remove-propose. On both sources a session has read-only tools, Read, Glob and Grep over the repo and no other tool, fenced as the walk's are. From the walk, a session is given today's date, the product's promise, the capability's area, name and promise, its footprint (source files with their line counts, and the tests, docs and other files the walk named, as it wrote them), and its placed PRs and changes whole, with no docs given up front, since it reads them with its tools. A footprint stored without a line count shows none. When this is more than one session holds, it goes in shares as before, each share carrying the footprint. The recovering skill describes the tools, what a session is given and the three why rules of §6. An anchor is `from <path>` for a doc, a test or a source file as well as for a PR or change. No file path may appear in a heading, a body or a `Because:` line: Physa finds one in the text the session wrote (not in the lines it generates when it splits the text into the folder's files), sends it back with the map check's problems, and drops the entry with its reason after the retries. The product's promise is the stored proposal's when one is stored, else "Not yet stated.", since the walk gives none (decided by Claude for the owner to review).
   Capabilities run in a seeded order: areas, and the capabilities of each, are shuffled by the seed, and one capability is taken from each area in turn, round after round, so a run that stops early leaves a sample spread across the areas. The order depends only on the set of capabilities and the seed. The seed is derived from the gather's time, so a gather always gives the same one, and is kept in init's record on the first full recovery from the walk and reused by every later `--recover`, until a new gather clears it. A new gather thus gives a fresh sample, and a continued run keeps its order (decided by Claude for the owner to review; a fixed default would be as reproducible but every repo and gather would share one order). `--recover --only` names walk capabilities and keeps its order, and stores no seed. The full run keeps the proposal until remove-propose. Not built yet: remove-propose.
6. **Consolidate** (Q10, the owner's: "we may need another pass at the end that de-dupes or merges rules that are similar. We may end up with noise."). Four steps, in this order:
   1. **Capability merge**, before the lift. The walk puts two areas' view of one promise into two capabilities (a name and its `-2`), and recovery writes the same rules under both. Discourse run 2 lifted 71 rules to the product and 66 of them joined two areas that held one promise; the product's rules reached 432 lines against a budget of 150. So a session first names the capabilities that are one promise, among groups code found, and code merges each group by architecture 12 §3's rules.
   2. **Exact duplicates** are found without a session.
   3. **One session per area**, given only its capabilities' entries, merges near-duplicates keeping every anchor, moves a rule to the capability it belongs to, and drops a question another entry answers.
   4. **The lift.** Rules repeated across areas, after the merge, go to the product's rules when a session judges them one rule, within the product's rules budget of 150 lines. A lift that would pass it is refused and reported, never trimmed.

   It never writes a new entry. Code refuses any id that is not among a session's inputs, and any entry or text with no source among them, and init's report says what it merged, moved, dropped, lifted and refused.
   Built as the change consolidate: `physa init --consolidate` runs over the capabilities recovered from the walk path, and not over a recovery from the proposal. Its sessions are prompt-only, with no tools, and choose by id among the entries and capabilities they are given; a choice naming anything else is refused item by item and the rest apply, and a reply that is not one JSON object gets one answer-now turn, after which its step is left as it was. A capability merge needs a candidate group with evidence (a walk rename by number suffix, or a rule repeated across areas), and a session's group must sit inside one. The merged promise is one of the group's own, named by the session, and the merged footprint is the union; the kept name's overview and area stay, and the other overviews are listed as dropped. A term name met twice with different definitions keeps the first and lists the other as a conflict. A merge over a size limit (rules, index, a duplicated heading) is refused and reported, and the capabilities stay as recovered. A capability whose candidate group no session judged lifts nothing, and its rules are reported as refused, so a rate limit cannot bring Discourse's failure back. A final check of the output with the map's form rules runs before anything is stored. The record is one row of init's `init_consolidate` table (§5), cleared by a new gather, new areas or a new walk, and `--write` uses it only while its fingerprint matches the recovered rows and the walk; a later recovery makes it stale, and `--write` then writes the map without it and says to run `--consolidate` again. `--consolidate` is a phase alone, not yet in the full run, and allowed with `--write`. It holds to `--cap` as the other phases with sessions do (§8), and each run's spend adds to init's record. Its output is plain text or `--json`, and its exit code is 0, or 1 when a session got no answer. The packages are `internal/repeats` (candidates), `internal/consolidating` and `internal/capabilitytext` (merging without sessions), `internal/consolidateguard` (the source and conservation check), `internal/consolidateprompt` (skills, replies), `internal/consolidate` (the phase) and `internal/consolidatedmap` (what `--write` takes from it).
   Departures from architecture 12 §3, decided by Claude for the owner to review: the merged promise is a session's choice among the group's own, not a person's; stewards are not combined, since recovery writes none; and the walk and place rows keep their names, so the merged footprint lives in the consolidation record only. Follow-up, not built: a clone that rebuilds init's record from areas, walk and place gets the names unmerged, since those rows keep the names of capabilities merged away. A limit, known: `recovery.dedupe` drops, before rows are stored, any entry whose slug an earlier capability holds, so cross-area repeats that shared a slug never reach consolidation, and this change does not read them back from the rows' details. Remove-propose is not built.
7. **Check** and **review**, as today; review gains architecture 12's guide.

## 4. What a capability is

The walk works from the capability definition, settled by the owner ("I think that definition sounds right") and taken into the glossary's Capability entry:

> A promise the product makes to its users, stated as intended behaviour: something a user can rely on and would name, true however the code is arranged, and whose breaking someone would report. A capability can be large and is kept by many changes over time; a change that needs two capabilities usually means they are one.

With four tests: a user would name it; it survives a rewrite, so it never follows layers or folders; breaking it is a bug someone reports; a well-made change can belong to it alone. No prompt gives a count. The definition lives in the code, in the walk's skill, and a test fails when the glossary's Capability entry stops matching it (Q2, the owner: "code as source with a drift test"), so a change to the definition is one code PR that touches both, and is run before it ships. The glossary is never read into a prompt: Physa's map does not drive the binary. The owner, on promises that cut across layers: "For ME personally, I probably wouldn't architect a capability that way, but we can't put people into a box like that." So init assumes nothing about how a codebase is organized: in a codebase arranged by capability the walk finds promises and folders agree, and in a layered one it gathers each promise from every layer.

## 5. Init's record

The map holds no file paths (vision §4.1), so footprints and placement stay in init's record in `.git/physa`, beside the gather. Learning and architecture 12's review read them. A clone without the record (a teammate's, or one made after init) can rebuild it with the areas, walk and place phases alone, without recovering: on these repos that was $15 to $110 and under 90 minutes. Built: init's record is its own package, `internal/initrecord`, beside the store, which keeps every migration. Placements are one row of its `init_place` table, cleared by a new gather, new areas or a new walk. The seed of recovery's order is one row of its `init_recover` table, cleared by a new gather only, so new areas or a new walk keep the order of a continued run. The consolidation is one row of its `init_consolidate` table: the JSON record of what was merged, moved, dropped, lifted and refused, with the fingerprint of the recovered rows and the walk it came from, and the session spend. A new gather, new areas or a new walk clear it, and a recovery makes it stale without clearing it (§3 step 6).

## 6. The why

A rule needs a reason where its sources give one. Recovery takes reasons from PRs, changes, docs and code comments that say why. Legacy code won't always say why, and the owner: "I don't know that we will ALWAYS get a why on legacy codebases, that is a lot to ask." So (Q4):

- **A rule backed only by tests or comments stays a rule when its source shows intent**: a test named for a regression, a comment saying what would break, a test tied to a PR. Its `Because:` says what the source shows. A test is strong evidence a rule holds; the owner: "a rule backed by a test or comment is pretty defensible because of where it came from".
- **It is dropped when it only restates the code**, since the code and tests already hold the what (vision §4.1).
- **A question is only for an important gap a person could fill**, never for every rule without a PR. Mastodon run 2 turned every such rule into a question and left 1,601 questions for 752 rules.

## 7. The PR window

A window of 1,000 PRs reached back one month on Discourse and two and a half on Mastodon, leaving 31% to 47% of capabilities with no PR. Mastodon run 2 gathered 3,000 and held them within the cap. The default becomes twelve months of history (Q5), with `--max-prs` and `--since` as today and gather's top-up for quiet areas kept.

Built as the change gather-window: a bare gather asks for twelve months with no PR limit, and `--max-prs N` still stops at N. Twelve months of a large repo is enough requests to meet the forge's rate limits, so gather lists merged PRs a page at a time and waits a limit out as GitHub's docs say ([REST](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#exceeding-the-rate-limit), [GraphQL](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api#exceeding-the-rate-limit)): the `retry-after` given, else until the primary limit's reset, else a minute doubling on each repeat, up to 65 minutes in all. A gather the forge still stops is stored with every PR it listed, init says how far back they reach and why it stopped, and exits non-zero. The store marks it stopped with the date its PRs reach back to and the reason; `--propose` and `--recover` on it warn of that and still run, and a later gather starts again (02 §2.2). Resuming is the idea gather-resumes, not built.

## 8. The cap

No estimate. A person may give a run a cap, as the owner asked, and the run stops cleanly when the next session's budget would pass it. The cap is the person's to define, in the terms they pay in. The owner: "Subscription users probably don't care about a dollar amount but rather a percentage of their usage, or they may not want a cap at all, same goes for API users. This should be flexible." So a cap is one of:

- **none**, the default: init runs to the end;
- **an amount of money**, for people who pay by the token;
- **a share of their plan's usage**, for people on a subscription, written as a ceiling (`--cap 80%`: start nothing that would take the plan's usage past 80%). Claude Code reports it: `claude -p /usage --output-format stream-json --verbose` prints a `usage_report` whose rate limits give each window's percent spent and reset time, which the owner's afk reads to pause its runs near the limit;
- **tokens**, weighted by price as every spend in Physa is.

Whatever the unit, init counts spend as it always does and shows it in the unit the cap was given in. A bare run never asks for a cap (Q6): `--cap` is there for whoever wants one. Recovery goes in a seeded random order across areas, so a run stopped by the cap leaves a fair sample of the map rather than some areas whole and others untouched, and `physa init --recover` continues where it stopped. The seeded order is built (§3 step 5), and so is the cap, below. Init still says before it starts what a token is worth (02 §2.7) and after it ends what it spent. This replaces 02 §2.7's estimate, its ratio records and its "past the estimate" message.

Built as the change cap: `--cap` takes `$5` or `5usd` (money, to the cent), `80%` (a share of the plan's usage, above 0 and at most 100) or a count of weighted tokens written as an appetite is (`200k`, `1.5m`, `50000`); none is the default, and `--cap` with `--place` is refused, since `--place` starts no session. Every session any phase starts goes through one guard, so the cap is checked before discovery, each area's part, each walk, propose and its shares and merge, each capability's recovery and each retry, and each of consolidation's sessions. Before a session runs it is held to a budget: its system prompt and prompt twice over, since a one-turn session writes them to the 1-hour cache at twice input (10 §3), plus the 16,000-token reply reserve five times over, since output weighs five times input; when larger, the mean spend of the sessions this run has seen end, since sessions that read files with tools spend well beyond their prompt. For money and tokens a session would pass the cap when what init has spent, the budgets of the sessions already running and this session's budget together are over it, the budget priced at the default model's input price (with no price known it counts nothing); the check before the first session, on what init's record has spent, refuses when that already reaches the cap. For a share the cap is a ceiling: nothing starts while the plan's usage is at or over it, read before each session. The Claude Code adapter reads the most restrictive active limit, the highest percent of the limits the report marks active, because whichever one runs out stops the sessions, where `weekly_all` alone would miss a five-hour or model-scoped limit; a report with no active limit, or an agent that cannot report its usage, refuses to start: `physa init: --cap 80% needs the agent's plan usage, and <agent> cannot report its plan's usage: <why>`, exit 2. The usage is read without `ANTHROPIC_API_KEY`, as the plan's usage is the login's, while sessions use the key when it is set, and the existing warning says so. What the cap counts as spent is init's record's spend, phase by phase, plus this run's. Once the guard refuses a session it refuses every later one, and sessions already running finish, so a run can end past its cap by what they spend over their budgets. The run then prints `physa init: the cap of <cap> was reached: nothing more was started and sessions already running finished; init has spent <spend in the cap's unit>. To continue, run <line> with a larger --cap, or none.` (for a share, it gives the plan's usage and says to run the line once the usage is under the cap), nothing says a phase failed, and init exits 1; a capped run that ends whole says what it spent of its cap, and a stopped recovery in which a capability really failed still exits 2. A stopped gather keeps the earlier stored gather whole; areas, walk, propose and consolidate store nothing unless whole, and a stopped `--consolidate` starts again from the recovered capabilities, as every run of it does. `--recover` continues: it skips capabilities already recovered from the same gather and source (the walk's, or the proposal's) and keeps the seeded order, saying how many it kept, and a bare run stopped while recovering says `physa init --recover` with the words `--recover` takes. `--areas` and `--walk` start again whole, as the cap stops them before they store anything; keeping a partial walk is an idea of its own. The ratio records were in the machine's spend cache and are dropped on its next save. An interrupt (Ctrl-C or SIGTERM) stops a run the same way, built as the change context-commands of the pursuit go-architecture: the command's context is cancelled, nothing more starts, each running agent is sent SIGINT through its own context and given a moment to end, what finished stays in init's record, and init prints `physa init: interrupted: ...` with what was kept and the line to continue, keeping the `--cap` typed, and exits 130. A second interrupt ends the process at once, as before, for a run blocked where no context reaches, such as a question on the terminal.

## 9. What init reports

Its output and PR body report the measures the runs used: files in a capability, shared and unclaimed; PRs and changes placed; PRs in one capability (the change tenet, vision §4.2: "a change belongs to exactly one capability"); capabilities with no PR or change; where the rules' reasons came from; consolidation's counts (what it merged, moved, dropped, lifted and refused); and spend per phase.

Built as the change report: `internal/initreport` reads init's record (§5) with no session, no repo file, no forge and no environment, and gives each measure as counts. Each is defined as built:

- **Files**, over the source files the areas' split names: in a capability when exactly one walk capability owns the file; shared when the walk names it shared (a name ending in `/` covers every source file under it) or two or more capabilities own it; unclaimed, the rest. Named shared wins over owned.
- **PRs and changes placed.** PRs placed, of the PRs gathered, with the two reasons place gives for placing nowhere (no files known from the gather; none of its files belongs to a capability), each counted. Changes no gathered PR holds, placed, of their total, with the same two reasons. Changes a PR holds follow it and are given as a count.
- **PRs in one capability**, counted over the gathered PRs owning at least one source file of a capability: those whose owned files all belong to one capability, as a share of those PRs. The PRs left out, touching no such file, are counted beside it, so the number can be read beside the runs' (the lab's `compare.py`).
- **Capabilities with no PR or change**, of the walk's capabilities, by the walk's names even after a merge, since placements are keyed to them.
- **The rules' reasons**, over the rules `--write` would write (a current consolidation's, else the recovered rows'), by the first kind of anchor each rule has: a PR or change; a doc; a source file and a test; a test only; a source file only; none. A rule's `from` path is told a test, a doc or a source file by the areas' split. The report adds how many of the test-only rules carry a `Because:` line, and counts product rules among them, and says how many of either it could not read.
- **Consolidation's counts**, from the stored record while it is current: capability groups merged and capabilities merged away; entries merged exact and near; rules moved; questions dropped; rules lifted to the product; what was refused; and entries before and after with the product's rules after.
- **Spend per phase**, in run order (discover, areas, walk, propose, recover, consolidate): raw input, cached input and output tokens, weighted tokens and the cost estimate, with a total.

A measure whose inputs are not stored says why it can't be given, and never prints a zero: no areas, no walk or placements, no consolidation, or one gone stale because a later recovery changed the rows. In `--json` it is `{"cant_be_given": "<why>"}` and nothing else. A measure whose total would be zero says so in words (for example, no gathered PR touches an owned source file). The reasons are fixed prose, never a decode error's text, since that can quote a file path. The report holds counts and no file path, so it can go in a PR body.

It shows in three places. The PR body gets a `## Measures` section right after the capabilities proposed, with every measure but spend: the body's existing "Tokens spent" table already gives each phase and the total, so spend is not shown twice there. `--write` shows the report in its output, plain and as the `report` value inside `write` in `--json`. A full run that does not write prints it as plain text, or as a `report` key of `--json`, after recovery, and only when recovery finishes: a run stopped by `--cap` or an interrupt prints what it kept and the line to continue, not a report. The phases alone (`--walk`, `--place`, `--recover`, `--consolidate`) do not print it, each having its output. Decided by Claude for the owner to review: each definition above where this design left room (files by exact ownership, the left-out PRs counted, the first kind of anchor deciding a rule's reason, one spend table in the body, the phases alone not printing the report). Known: with a stored consolidation, `--write` reads the walk's source files twice to check the consolidation is current, only to count lines; the fingerprint never uses them.
